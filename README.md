# AI 越来越会写代码，为什么我们还是经常被打断？

今天，GitHub 官方博客发布了《The next developer interface is ambient intelligence》，讨论 AI、智能体、语音和实体交互如何改变软件开发：开发者可以更多地表达想实现什么，让工具承担具体操作。

这篇文章提出的方向很有意思：开发工具的进步，不只是增加功能，也在于减少操作对思路的打断。

来源：[GitHub 官方文章](https://github.blog/news-insights/company-news/the-next-developer-interface-is-ambient-intelligence/)

## 写得快，只是其中一步

设想一个常见的开发场景：

你让 AI 写出了功能雏形，接下来需要打开文档、安装依赖、查看仓库里的讨论，再运行测试。

代码生成可能只花了片刻，但整个任务能否顺利完成，还取决于后面的每一步。

文档是否找得到？环境是否准备好？需要访问的资源能否正常加载？生成的代码有没有通过验证？

**真正影响效率的，往往是这些步骤能否连续进行。**

## 比起再装一个工具，先找到反复卡住的地方

如果你也在使用 AI 辅助开发，可以记录一次任务中的等待：

| 遇到的情况 | 值得先检查的方向 |
| :--- | :--- |
| AI 反复理解错需求 | 是否提供了明确目标、约束和示例 |
| 示例代码运行失败 | 依赖版本与运行环境是否匹配 |
| 页面或下载请求超时 | 本地网络、目标服务状态与连接配置 |
| 生成结果看似正确却不能用 | 是否有实际测试和验收标准 |

不同的问题，需要不同的处理方式。换模型无法解决所有环境问题，换网络也无法修复代码逻辑。

把原因分清楚，比一遍遍重新开始更有用。

## 工具的价值，最终落在完成的事情上

今天这条开发动态带来的启发是：评估一个工具时，除了看它能做多少事，也可以看看它让你少做了多少重复操作。

少一次重新解释需求，少一次无目的的重试，少一次被打断后重新找回思路。

当这些小障碍逐步减少，AI 带来的速度，才更容易变成真正完成的项目。
